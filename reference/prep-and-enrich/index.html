Prep & Enrich Phases

Most pipelines are Extract → DQ → Transform → Load. Two optional phases slot in between Extract and DQ, and both exist for the same reason: some data cannot be validated honestly until it has been fixed or filled in first.

Phase Runs Ships in What it does
Prep Extract → Prep → Enrich Open core Mutates staging columns in place using cleanse ops, expressions, lookups.
Enrich Prep → Enrich → DQ @caracal-lynx/sluice-enrich (add-on) Async third-party API lookups; writes results into new staging columns.

Both run before DQ, deliberately. Fixing a postcode’s casing and then validating it is useful; validating it first and rejecting the row is not.

Ordering

Section titled “Ordering”

In multi-source pipelines, prep rules scoped with sourceId fire per source before the merge; rules without a sourceId fire once after the merge, against stg_merged.

Prep — Phase 12

Section titled “Prep — Phase 12”

Prep mutates an existing staging column in place. It adds no columns and drops no rows; it rewrites values so that Enrich and DQ see already-corrected data.

The classic case: a legacy system pads account codes to ten characters with spaces, and your DQ pattern rule rejects every one of them. You could loosen the pattern — or you could trim the column once in prep and keep the rule strict.

Rule keys

Section titled “Rule keys”
Key Type Default Notes
field string — Required. An existing column, mutated in place.
cleanse string — Pipe-separated cleanse chain. See Transforms → Cleanse operations.
expression string — expr-eval expression, or js: prefix for the vm sandbox.
lookup string — Name of a prep.lookups[] entry.
when string — Optional row predicate. Falsy → the rule is skipped for that row and counted in rowsSkipped.
onMiss enum keep Lookup misses only. keep leaves the value untouched; null overwrites with SQL NULL; error throws and halts the run.
sourceId string — Multi-source only. Scopes the rule to one pre-merge source. Rules with no sourceId run post-merge.

Exactly one of cleanse, expression, or lookup must be set on each rule — the schema rejects zero or two. onMiss is only valid alongside lookup.

Rules are ordered and cumulative

Section titled “Rules are ordered and cumulative”

Rules apply top-to-bottom and later rules see earlier rules’ mutations. That is the point — chain a trim, then a lookup against the trimmed value, then an expression over the result.

When prep runs

Section titled “When prep runs”

Unlike Enrich, prep runs even under --dry-run and sluice validate, because DQ depends on its output. A validate run that skipped prep would report violations the real run would never produce.

Prep summary JSON

Section titled “Prep summary JSON”

Prep writes {outputDir}/{pipeline.name}-prep-summary.json (override with prep.summaryFile). One entry per firing — one for a single-source pipeline, up to N + 1 for multi-source:

rowsChanged counts rows where the new value actually differed from the old one, so a rule reporting rowsChanged: 0 across a full dataset is a rule that is not earning its place.

A prep failure exits with code 5.

Enrich — Phase 4a

Section titled “Enrich — Phase 4a”

Enrich calls external APIs and writes the answers into new staging columns, so DQ rules can then validate against a third party rather than against a regex.

The schema, the public EnrichPlugin interface, and the injection hook are all in the open-source core. The framework that executes the phase — the provider registry, the concurrency runner, the cache — lives in the private @caracal-lynx/sluice-enrich package. See Commercial Support.

Silently skipped when not installed

With the private package absent, an enrich: block is still parsed and validated — but the phase is skipped with a WARN log and the run continues. If your DQ rules reference enrich output columns, they will validate against columns that were never written. Check the log rather than assuming enrich ran.

enrich keys

Section titled “enrich keys”
Key Type Default Notes
cache boolean | "persist" true true in-memory for the run; "persist" on disk between runs; false disables caching.
onError flag | skip | fail flag Pipeline-wide policy. flag marks the row and keeps it; skip drops it; fail halts.
lookups object[] — Required, minimum one entry.

enrich.lookups[] keys

Section titled “enrich.lookups[] keys”
Key Type Notes
field string Required. The staging column whose value is sent to the provider.
provider string Required. Provider id (e.g. vies, hmrc).
writeColumns object Required. Must contain valid:; any further keys map provider data fields to staging column names.
preValidate string Optional rule id applied before the call — skip a network round-trip on a value that is malformed anyway.
onError enum Per-lookup override of the pipeline-wide onError.
cache boolean Per-lookup override of the pipeline-wide cache.
options object Arbitrary per-provider config, passed through verbatim.

Tuning from run:

Section titled “Tuning from run:”

These live in the run: block and are consumed by the private package if installed:

Key Default Notes
enrichConcurrency 5 Concurrent in-flight provider requests.
enrichTimeoutMs 5000 Per-request timeout.
enrichMaxRetries 3 Max retries per call (0–5).

When enrich runs

Section titled “When enrich runs”

Enrich is skipped when the pipeline is a --dry-run or sluice validate run, when --no-enrich is passed, or when the private package is not installed. An enrich failure exits with code 4.

Writing an enrich provider

Section titled “Writing an enrich provider”

EnrichPlugin is the only plugin interface in Sluice permitted to perform I/O — every other plugin type is contractually pure and synchronous.

Drop it in as a *.enrich.ts file in your plugins/ directory; the private package’s loader discovers it through the registered phase factory.
