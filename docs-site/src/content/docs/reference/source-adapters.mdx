title: Source Adapters

A Sluice **source adapter** is the component that reads raw data from a system and stages it in DuckDB for downstream DQ, transform, and load. Sluice ships with seven built-in source adapters covering the patterns most data migrations need: SQL Server, PostgreSQL, CSV, XLSX, REST, Odoo CSV exports, and local JSON files.

This page is the reference for each adapter's `source:` configuration. For the broader pipeline structure, see [Pipeline YAML Schema](/sluice/reference/pipeline-yaml/).

## Common config

Every source has the same `adapter` + at least one of `query` (for SQL adapters), `file` (for file adapters), or `endpoint` (for REST). The `adapter` value is one of:

```
mssql | pg | csv | xlsx | rest | odoo-csv | json
```

Sluice does not ship ERP-specific **source** adapters — reading out of IFS, Business Central, or BlueCherry is usually a SQL query or a REST call, which the `mssql`, `pg`, and `rest` adapters already cover. For anything genuinely bespoke, implement the `SourceAdapter` interface as a plugin — see [Plugin System](/sluice/guides/plugin-system/).

## `mssql` — Microsoft SQL Server

Streams query results from a SQL Server database into the DuckDB staging table. Trusted authentication and SQL authentication are both supported.

```yaml
source:
  adapter: mssql
  connection: ${SOURCE_MSSQL}
  query: |
    SELECT c.CUST_CODE, c.CUST_NAME, c.POST_CODE
    FROM dbo.Customers c
    WHERE c.Active = 1
```

| Key          | Type   | Notes                                                                                                                                            |
| ------------ | ------ | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| `connection` | string | Connection string. Either `mssql://user:pass@host/database` or a JSON string for trusted/advanced config. Resolved from `${ENV_VAR}` at runtime. |
| `query`      | string | The full SELECT statement to stream. **Required** unless `table` is set in a future release.                                                     |

**Type mapping (SQL Server → DuckDB):**

| SQL Server                    | DuckDB      |
| ----------------------------- | ----------- |
| `varchar`, `nvarchar`, `char` | `VARCHAR`   |
| `int`, `bigint`               | `BIGINT`    |
| `decimal`, `numeric`, `money` | `DOUBLE`    |
| `bit`                         | `BOOLEAN`   |
| `datetime`, `date`            | `TIMESTAMP` |
| `float`, `real`               | `DOUBLE`    |

**Notes:**

- Results are streamed via `request.stream = true` so memory stays bounded for large extracts.
- Trusted connections are detected by `trustedConnection: true` in a JSON connection config.

## `pg` — PostgreSQL

```yaml
source:
  adapter: pg
  connection: ${SOURCE_PG}
  query: SELECT id, name, email FROM customers WHERE active = true
```

| Key          | Type   | Notes                                                                         |
| ------------ | ------ | ----------------------------------------------------------------------------- |
| `connection` | string | Standard PostgreSQL connection string. Resolved from `${ENV_VAR}` at runtime. |
| `query`      | string | The SELECT statement to stream.                                               |

## `csv` — CSV files

Reads one or more CSV files into the staging table. Glob patterns are supported — multiple matching files are concatenated into a single staging table.

```yaml
source:
  adapter: csv
  file: ./data/customers.csv
  delimiter: ","
  encoding: utf-8
```

| Key         | Type   | Default | Notes                                      |
| ----------- | ------ | ------- | ------------------------------------------ |
| `file`      | string | —       | Path or glob (e.g. `./data/export-*.csv`). |
| `delimiter` | string | `,`     | Field delimiter.                           |
| `encoding`  | string | `utf-8` | File encoding.                             |

**Notes:**

- Parse options are `{ columns: true, skip_empty_lines: true, bom: true }` — the BOM is stripped automatically, which matters for Excel-generated CSVs.
- All columns are inferred as `VARCHAR` in DuckDB. Type coercion happens later, in the transform phase.

## `xlsx` — Excel workbooks

Read-only access to `.xlsx` files via [`read-excel-file`](https://www.npmjs.com/package/read-excel-file).

```yaml
source:
  adapter: xlsx
  file: ./data/customers.xlsx
  sheet: "Customer Export"
```

| Key     | Type             | Default | Notes                                              |
| ------- | ---------------- | ------- | -------------------------------------------------- |
| `file`  | string           | —       | Path to the workbook.                              |
| `sheet` | string \| number | first   | Sheet name, or 0-based index into the sheet order. |

**Notes:**

- The first row is treated as the header row; every remaining row is emitted keyed by those headers. All columns stage as `VARCHAR` — type coercion happens later, in the transform phase.
- Formula cells resolve to their **cached result**, and date cells arrive as real dates rather than Excel serial numbers.
- A warning is logged if the workbook has more than one sheet and `sheet` is unset; the first sheet is used.
- Sluice does not write XLSX. For Excel-shaped output, use the `csv` target adapter and let the consumer open it in Excel.

:::note[Reader history]
`read-excel-file` replaced `exceljs` in July 2026, which had itself replaced `xlsx`/SheetJS. Both predecessors were dropped over unpatched transitive advisories. Do not "simplify" back to either — see [ADR-0001](https://github.com/caracal-lynx/sluice/blob/master/docs/adr/0001-replace-exceljs-with-read-excel-file.md).
:::

## `rest` — HTTP REST APIs

Pulls JSON payloads from an HTTP endpoint and flattens nested fields into staging columns. Three pagination modes are supported: `offset`, `cursor`, and `page`.

```yaml
source:
  adapter: rest
  endpoint: ${API_BASE}/customers
  headers:
    Authorization: Bearer ${API_TOKEN}
    Accept: application/json
  pagination:
    type: offset
    pageSize: 100
    pageParam: skip
    totalField: data.total
    dataField: data.items
```

### Top-level keys

| Key          | Type   | Notes                                                  |
| ------------ | ------ | ------------------------------------------------------ |
| `endpoint`   | string | Full URL. `${ENV_VAR}` tokens are resolved at runtime. |
| `headers`    | object | Optional. Added to every request.                      |
| `pagination` | object | Optional. Omit for single-page responses.              |

### Pagination modes

#### `type: offset`

```yaml
pagination:
  type: offset
  pageSize: 100
  pageParam: skip # query param name for the offset
  totalField: data.total # dot-path to total count in the response
  dataField: data.items # dot-path to the records array
```

Sluice issues `?skip=0&top=100`, `?skip=100&top=100`, … until it has fetched `data.total` records.

#### `type: page`

```yaml
pagination:
  type: page
  pageSize: 50
  pageParam: page # query param name for the page number
  totalField: meta.totalPages
  dataField: results
```

Sluice fetches pages 1, 2, 3 … up to `meta.totalPages`.

#### `type: cursor`

```yaml
pagination:
  type: cursor
  pageSize: 100
  pageParam: limit
  cursorField: nextCursor # field in response body to read next cursor from
  cursorParam: cursor # query param name to send the cursor in
  dataField: items
```

Sluice fetches until the response's `nextCursor` is absent or null.

### Notes

- Retries: `axios-retry` with **3 retries**, exponential backoff, retrying on `429` and `5xx`.
- Nested JSON fields are flattened using `__` as a separator: `address.postCode` becomes a `address__postCode` column in staging.

## `odoo-csv` — Odoo CSV exports

A `csv` reader with one extra trick: Odoo exports a repeating attribute column (canonically **Variant Values**) as `Key: value` text, and spills additional entries onto **continuation rows** where every other column is blank. This adapter merges those continuation rows back into their parent row and pivots each key into its own column.

```yaml
source:
  adapter: odoo-csv
  file: ./data/product-variants.csv
  delimiter: ","
  pivot:
    column: Variant Values
    keys: [Colour, Size, Fabric]
    onUnknownKey: warn
    dropOriginal: true
```

| Key         | Type   | Default | Notes                                                       |
| ----------- | ------ | ------- | ----------------------------------------------------------- |
| `file`      | string | —       | Path or glob, same as the `csv` adapter.                    |
| `delimiter` | string | `,`     | Field delimiter.                                            |
| `encoding`  | string | `utf-8` | File encoding.                                              |
| `pivot`     | object | —       | The pivot declaration. Omit it and this behaves like `csv`. |

### `pivot` keys

| Key            | Type     | Default | Notes                                                                                                                                    |
| -------------- | -------- | ------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| `column`       | string   | —       | The source column carrying `Key: value` entries. Continuation rows are detected as rows where every column **except** this one is empty. |
| `keys`         | string[] | —       | Expected key names. Each becomes a new output column populated with that key's value.                                                    |
| `onUnknownKey` | enum     | `warn`  | `warn` adds a column named after the unexpected key and logs a warning; `error` halts the run.                                           |
| `dropOriginal` | boolean  | `true`  | When true the pivot column is removed from the output; when false it carries the parent row's raw value through.                         |

**Notes:**

- Every column stages as `VARCHAR`, exactly as with `csv`.
- `onUnknownKey: error` is the right setting once you know the full key set — it turns a silently-dropped attribute into a failed run.

## `json` — Local JSON files

Reads a single JSON file from disk and flattens it into staging columns. This is the local-file counterpart to `rest`; it makes no HTTP requests.

```yaml
source:
  adapter: json
  file: ./data/scan-results.json
  recordPath: data.items
```

| Key          | Type   | Default | Notes                                                                                                             |
| ------------ | ------ | ------- | ----------------------------------------------------------------------------------------------------------------- |
| `file`       | string | —       | Path to the JSON file.                                                                                            |
| `recordPath` | string | —       | Dot-path to the records array inside the file (e.g. `data.items`). Omit when the file's root is already an array. |
| `encoding`   | string | `utf-8` | File encoding.                                                                                                    |

**Notes:**

- Nested objects are flattened with `__`, the same separator the `rest` adapter uses: `address.postCode` becomes `address__postCode`.
- Nested **arrays** land as JSON text in a single `VARCHAR` column.
- The value at `recordPath` must be an array, and it must be non-empty — a `VARCHAR` staging schema cannot be inferred from zero rows, so an empty result raises a `SourceError` rather than staging an empty table. If an empty extract is a legitimate outcome for your job, skip the run in your orchestration rather than letting it fail.
- If the root of your file is an object keyed by something else (many scanners emit this shape), reshape it into an array first — a few lines of `jq` or a small script — then point Sluice at the result.

## Multi-source pipelines

To consolidate data from multiple sources into one target, use the multi-source form. Each source needs an `id`, a `priority`, and (optionally) a `rename` map to harmonise column names from CSV/XLSX sources.

```yaml
sources:
  - id: sql-server
    priority: 1
    adapter: mssql
    connection: ${SOURCE_MSSQL}
    query: SELECT STYLE_NO, STYLE_DESC, COST_PRICE FROM dbo.Styles
  - id: excel
    priority: 2
    adapter: xlsx
    file: ./data/product-data.xlsx
    sheet: "Products"
    rename:
      Style Number: STYLE_NO
      Description: STYLE_DESC
      Fibre: FIBRE_CONTENT
```

Combined with the [`merge:`](/sluice/reference/pipeline-yaml/) block, sources can be joined with strategies like `coalesce`, `priority-override`, `union`, or `intersect`. See [Data Migration Patterns → Pattern 3](/sluice/guides/data-migration-patterns/) for a worked multi-source example.

## Custom source adapters

Need to read from a system Sluice doesn't ship a built-in adapter for? Implement the `SourceAdapter` interface as a Tier 2 file plugin or a Tier 3 npm package — see the [Plugin System](/sluice/guides/plugin-system/) guide.
