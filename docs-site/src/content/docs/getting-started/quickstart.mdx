This page takes you from a clean machine to a working pipeline run with data quality validation, transformation, and a rejection report — all in **under ten minutes**.

By the end you will have:

- A pipeline YAML that reads a CSV of customers, validates emails, normalises field casing, and writes a clean CSV.
- A rejection CSV showing every row that failed a data quality check, with the rule and severity recorded.
- A DQ summary JSON suitable for dropping into a CI artefact.

## Before you start

Install the CLI globally if you haven't already — see [Installation](/sluice/getting-started/installation/). The rest of this page assumes `sluice --version` works in your shell.

> **Shell shown:** PowerShell 7 on Windows. Every command also works as-is in Bash, Zsh, and Fish — Sluice does not depend on shell-specific features.

## The pipeline

<Steps>

1. **Make a working directory.**

   ```powershell
   New-Item -ItemType Directory -Path sluice-quickstart -Force | Out-Null
   Set-Location sluice-quickstart
   New-Item -ItemType Directory -Path data, output -Force | Out-Null
   ```

2. **Create a CSV with a few good rows and a few bad ones.**

   Save this as `data/customers.csv`:

   ```csv
   name,email,country
   Ada Lovelace,ada@example.com,GB
   Grace Hopper,grace@example.com,US
   Alan Turing,alan@example.com,GB
   Margaret Hamilton,not-an-email,US
   ,empty-name@example.com,GB
   Linus Torvalds,linus@example.com,FI
   ```

   Two of those rows are deliberately broken. The fourth row's `email` is not a valid email; the fifth row has an empty `name`. We're going to ask Sluice to catch both.

3. **Write the pipeline YAML.**

   Save this as `customers.pipeline.yaml`:

   ```yaml
   pipeline:
     name: customers-quickstart
     client: demo
     version: "1.0"
     entity: Customer
     description: First-pipeline walkthrough — CSV in, clean CSV out.

   source:
     adapter: csv
     file: ./data/customers.csv

   dq:
     # false so the run continues past the deliberate critical violation below and
     # still writes the target file. The critical row is excluded from the output
     # either way — see the note after step 6.
     stopOnCritical: false
     rejectionFile: ./output/customers-rejected.csv
     rules:
       - field: name
         checks:
           - { type: notNull, severity: critical }
       - field: email
         checks:
           - { type: notNull, severity: critical }
           - { type: email, severity: warning }
       - field: country
         checks:
           - { type: allowedValues, value: [GB, US, FI, DE, FR, IE], severity: warning }

   transform:
     fields:
       - { from: name, to: Name, type: string, cleanse: trim|titleCase }
       - { from: email, to: Email, type: string, cleanse: trim|lowercase }
       - { from: country, to: Country, type: string, default: GB, cleanse: trim|uppercase }
       - { to: Source, type: constant, value: "quickstart" }

   target:
     adapter: csv
     output: ./output/customers-clean.csv
     includeHeader: true
   ```

   Take a moment to read the YAML. The four sections — `source`, `dq`, `transform`, `target` — describe the **whole** migration. There is no other code to write.

4. **Validate the config.**

   ```powershell
   sluice check customers.pipeline.yaml
   ```

   `check` parses the YAML against the Zod schema and exits cleanly if everything is well-formed. If you mistype a key it tells you exactly where.

5. **Do a dry run.**

   ```powershell
   sluice validate customers.pipeline.yaml
   ```

   `validate` extracts, runs DQ, and applies transforms — but **does not load** to the target. This is the safe way to iterate on rules and mappings.

   You'll see a phase-by-phase progress bar, then a summary line:

   ```
   [1/3] [EX] Extract        [ok]    6 rows  0.0s
   [2/3] [DQ] Data quality   [fail]  6 rows  0.0s
   [3/3] [TX] Transform      [ok]    5 rows  0.0s
   [warn] · customers-quickstart · 6 rows extracted · 1 warnings · 5 loaded · 0.1s
   ```

   `Data quality` shows `[fail]` because a `critical` check fired — that is the phase
   reporting what it found, not the run aborting. Transform emits **5** rows, not 6:
   the empty-name row was dropped.

6. **Run the full pipeline.**

   ```powershell
   sluice run customers.pipeline.yaml
   ```

   `run` does everything `validate` does, then loads the clean rows to the target adapter. For our CSV target that means writing `output/customers-clean.csv`.

</Steps>

## Inspect the output

Five files land in `./output/`:

```powershell
Get-ChildItem output
# customers-clean.csv                     ← the loaded rows, with transformed columns
# customers-rejected.csv                  ← every DQ violation, one row per violation
# customers-quickstart-dq-summary.json    ← machine-readable DQ summary
# customers-quickstart-state.json         ← run state (for incremental mode)
# customers-quickstart.duckdb             ← the staging database; safe to delete
```

That last one is the DuckDB staging file. It is rebuilt from scratch on every run, so you can delete it freely — or open it in the DuckDB CLI and query `stg_raw` and `stg_transformed` directly when something looks wrong.

`customers-clean.csv` looks like this:

```csv
Name,Email,Country,Source
Ada Lovelace,ada@example.com,GB,quickstart
Grace Hopper,grace@example.com,US,quickstart
Alan Turing,alan@example.com,GB,quickstart
Margaret Hamilton,not-an-email,US,quickstart
Linus Torvalds,linus@example.com,FI,quickstart
```

Five rows out of six. Notice what changed:

- `name` → `Name`, `email` → `Email`, `country` → `Country` (renamed by `to:`), and every row gained a constant `Source` column.
- **Margaret Hamilton is still here**, bad email and all. Her `email` check was a `warning`, and warnings never remove a row — they only record it.
- **The empty-name row is gone.** Its `notNull` check on `name` was `critical`, and critical violations exclude the row from the output.

The rejection CSV records both:

```csv
row_index,field,value,rule,severity,message
3,email,not-an-email,email,warning,email is not a valid email address
4,name,,notNull,critical,name must not be null or empty
```

`row_index` is **0-based** and counts data rows, not file lines — so `3` is Margaret's row (the fourth data row) and `4` is the empty-name row.

That distinction — `critical` removes the row, `warning` keeps it but flags it — is the heart of the data quality model. See [Data Quality Rules](/sluice/reference/dq-rules/) for the complete reference.

### About `stopOnCritical`

The pipeline above sets `stopOnCritical: false`. The **default is `true`**, and it behaves differently in a way worth understanding before you write a real pipeline:

```yaml
dq:
  stopOnCritical: true # the default
```

With the default, that one critical violation **halts the run before the load phase**. You get the rejection CSV and the DQ summary, exit code `2`, and **no `customers-clean.csv` at all** — the point being that a pipeline quietly loading 5 of 6 rows into a production ERP is usually worse than one that stops and tells you.

Set it to `false`, as this walkthrough does, when you want the clean rows anyway and intend to work through the rejections separately. Either way the critical row never reaches the output.

## What just happened?

Sluice ran five phases:

1. **Config load** — parsed and validated the YAML against the Zod schema.
2. **Extract** — read `data/customers.csv` into an embedded DuckDB staging table called `stg_raw`.
3. **DQ** — ran every rule against `stg_raw` and wrote the rejection CSV and summary JSON.
4. **Transform** — applied your `cleanse` ops, `default`s, and `constant` to produce `stg_transformed`, excluding rows with critical violations.
5. **Load** — wrote `stg_transformed` to the target CSV, then wrote the run state file.

Two further phases — [**Prep** and **Enrich**](/sluice/reference/prep-and-enrich/) — slot in between Extract and DQ when a pipeline configures them. This one doesn't, so they were skipped.

Want to see the diagram of how the phases fit together? Read [How It Works](/sluice/architecture/how-it-works/).
